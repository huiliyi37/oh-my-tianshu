# Agent Note: TUI image paste / clipboard and the vision bridge (opencode-tui port)

Status: implemented

English | [中文](2026-08-13-tui-image-paste-and-vision-bridge.zh.md)

## Problem

The TUI input box ported the engine primitives (InputLine image state machine, term-image encoding, image-attach loading, OSC52 output) but never wired them: `app.ts` treated `onPaste` as plain text, had no Ctrl+V handling, dropped the `images` argument from `onSubmit`, never drained `takeClipboardOut`, and rendered no `📎` marker. `clipboard-image.ts` (system-clipboard image reading) was missing entirely. The opencode-tui input surface — paste image / paste image path / clipboard text fallback / OSC52 copy / inline terminal image rendering / vision-state hints — was effectively absent.

## Decision

Port the opencode-tui input surface and its model-side image path into dsh seams:

- **`engine/clipboard-image.ts`** (new, Apache-2.0 port): system-clipboard image reading via platform shells (macOS osascript + sips TIFF→PNG, Linux wl-paste/xclip, Windows PowerShell) with an injectable `setClipboardReader` seam for tests, plus `readTextFromClipboard` (pbpaste/wl-paste/xclip/Get-Clipboard) and `FOCUS_DEBOUNCE_MS` overlay-return focus debounce. The upstream `@mariozechner/clipboard` native path was **removed** (dsh does not declare that dependency; a dead dynamic import only adds noise — git history preserves it for re-adoption).
- **`app.ts` wiring**: `onPaste` first tries the clipboard image (attaching it and swallowing the byte garbage), then image-path detection (`looksLikeImagePath` + `loadImageAttachment`), then plain text; Ctrl+V → `handleCtrlV` (focus debounce → clipboard image → text fallback); every `inputLine.handleKey` drains `takeClipboardOut` to OSC52; the live region renders `imageSummary()` (`📎 N images`) above the input line; `handleSubmit(text, images)` normalizes images (`normalizeSubmitImages`), fills an empty text with `📎 图片消息`, renders the user bubble via `commitUserPrompt` and forwards images through `adapter.send.followup(text, images)`.
- **Terminal image rendering**: `commitUserPrompt` renders the bubble synchronously, then prepares images asynchronously (`prepareTermImageForCommit`) and appends the kitty/iTerm2 graphic sequence in the same commit-window protocol (clear live region → `writeRaw` → re-render). Local transcoding is millisecond-scale and precedes any network-bound assistant output, so the image lands under its bubble in practice; dsh has no enqueueMainCommit queue (opencode's), the residual race window with streaming commits is accepted and documented.
- **Model side**: `ImageBlock` (`{ type: 'image', dataUrl, mime? }`) joins the merge-extensible `ContentBlockMap`; `llm-deepseek` serializes user image blocks to OpenAI-style `image_url` content parts; the agent loop already passes `UserMessage` content through verbatim (`session.deriveMessages()`), so images reach the wire with no loop change. Compaction filters image blocks to text (they do not survive summaries) — accepted semantics.
- **Vision bridge** (new plugin `packages/context/vision-bridge`): when the primary model cannot see images (`primarySupportsVision: false`) and a vision model is configured (`provider`/`model`), `agent/pre-step` replaces image-carrying user messages with `[图片描述]\n<description>\n\n<text>` — the description is generated by `describeImages` (an `purpose: 'vision-description'` llm call, prompt auto-selected between generic structure and OCR-level transcription on UI/error keywords). Bridge failure/empty output degrades to visible `[图片桥接失败]`/`[图片桥接提示]` text; the turn never fails. **Model-visible ⟺ logged**: the description lands in session events; the raw image never reaches a text-only primary and never enters the session log. An optional `fallback` vision model (`{ provider, model }`) retries the description once when the primary vision model errors or aborts (5xx/timeout), and `describeImages` validates image data URLs (format + payload length) before calling out. `visionAutoBridge: true` makes `provider`/`model` optional: the route is resolved at call time by scanning registered providers' advisory catalogs for the first `supportsVision: true` model (via `LlmModelInfo.supportsVision`) — opencode-tui `visionModel.fallback` / `visionAutoBridge` / data-URL-check parity.
- **TUI vision hints**: `setVisionInfo` + three bubble states (image forwarded / bridged via vision model / not sent when no bridge). When the primary cannot see images and no bridge is configured, the TUI submits without images (the bubble already warned) — the "not sent" state is enforced at the submit boundary, not left to the model layer.

## Alternatives considered

### Bridge as an agent-loop change instead of a plugin

Rewriting `agent-loop` to describe images inline would couple the loop to a second model route and a vision policy. The `agent/pre-step` waterfall is the existing extension point (spark-anchors precedent): the bridge is an opt-in plugin over a stable surface, zero cost when absent.

### Keeping the upstream native clipboard dependency

`@mariozechner/clipboard` is undeclared in dsh; dynamic import of an undeclared optional dependency is dead code that knip would flag. The shell chain (osascript on macOS) covers the same path; the native route is recoverable from the opencode-tui source when a consumer actually needs it.

### TUI-side image filtering vs model-side dropping

With no vision bridge, dropping images at the model layer would require a loop-level policy and would log an image the model never saw. Filtering at the TUI submit boundary (the bubble has already warned "图片未发送") keeps the session log truthful: nothing that never reached the model enters it.

### Full vision-service port (ask_image / registry / cache)

The opencode-tui vision-service also ships an image registry, a description cache, and an `ask_image` re-interrogation tool. That is a second agent-facing tool surface beyond the input-box scope; it is deferred (see below) and recorded in Known Limitations.

## Consequences

- The TUI input box now matches the opencode-tui surface for paste/copy/image preview; image messages flow end-to-end (clipboard → input line → session → wire → vision model or primary) with the model-visible ⟺ logged invariant preserved.
- `app.ts` grew (+292, budget raised to 2538); the C4 controller-ization direction continues.
- Vision capability is **configuration**, not capability lookup: `primarySupportsVision` and the TUI `vision` hints are set by the assembler from the same source; the llm service has no vision-capability declaration yet.
- DeepSeek wire support for `image_url` is implemented but **not e2e-verified against a live vision-capable DeepSeek model** in this change (no keyed real-API test was run); if the API rejects image parts, serialize degrades to text markers and the vision bridge becomes the only image path — the adapter's `supportsVision` fact should then be recorded here.

## Deferred

- `ask_image` tool, imageRegistry, vision description cache (same-angle re-query hits zero calls), Settings vision-model panel — the opencode-tui vision-service remainder.
- llm provider vision-capability declaration (would replace `primarySupportsVision` configuration).
