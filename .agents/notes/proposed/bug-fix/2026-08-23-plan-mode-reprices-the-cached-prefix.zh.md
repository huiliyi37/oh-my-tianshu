# Agent Note: 计划模式重定价缓存前缀

Status: proposed

[English](2026-08-23-plan-mode-reprices-the-cached-prefix.md) | 中文

## 问题

进入或离开计划模式会在会话中途改写系统提示词，从而让供应商为整段对话缓存的前缀失效。每个计划周期为此付两次，而第二次恰好落在对话最长的时候。

[`plan-mode`](../../../../packages/plan/plan-mode/src/index.ts) 注册了一个 order 为 50 的 `plan:policy` 段落，其文本是会话状态的函数：计划模式激活时返回策略正文，否则返回空串。正文约 2345 个字符、分六段，而 order 50 把它排在 100–199 的工具指引带之前，所以一次开关连带顶掉它后面的每一个工具段落。

这个段落自己的文字点明了它没能解决的问题：「The tool catalog stays the same across modes for request-cache stability. These plan-mode rules override any later tool description or guidance that suggests using mutation tools; those tools remain listed only to keep the request shape stable.」计划模式已经认识到随模式变化的请求形状要付缓存代价，并冻结了工具目录来保护它——却把随模式变化的字节写进了系统提示词，而系统提示词排在工具与整段消息历史之前，作废的范围因此严格大于它所保护的那份目录。

## 未命中的 token 究竟去了哪

高总体命中率与昂贵的单次失效可以并存，这正是命中率百分比不适合用来量这件事的原因。已记录的 DeepSeek 会话输入命中率为 99.4%，而剩下的 0.6% 并非同一回事。把 44 个不少于 30 步的会话里每一个未命中 token 按其前一个事件归类：

| 未命中 token 的来源 | token | 占比 | 可回收 |
|---|---|---|---|
| 会话的第一次请求 | 346,007 | 3.0% | 否——此时尚无缓存 |
| 紧随 `request/header` 变化之后的一步 | 1,517,892 | 13.1% | **是** |
| 其余各步 | 9,711,118 | 83.9% | 否——新产生的输出与工具结果 |

83.9% 是主项，且不是缺陷：每一步都追加上一条助手消息及其工具结果，而尚不存在的 token 不可能被缓存过。它约为每次请求 3,400 个未命中 token，也解释了为什么一个前缀完全没变的会话仍会显示百分之几的未命中。会话 `66b260f8`、`d991953b`、`545856ce`、`e09a6b2b` 各自只发出一次 header、完全没有失效，它们的未命中量全部属于此项。

13.1% 是可回收的那部分，而且高度集中。在 `7635e035`（336 步）里，仅两次计划模式切换就重定价了 115,683 与 146,074 个 token——合计 261,757，占该会话全部未命中量的 53%。`1b4e7f75` 达到 66.0%，`7e29a310` 61.8%，`15a62c0d` 55.0%，`940cd8c9` 49.6%。

## 打断清单

那 44 个会话里共发生 26 次 header 变化，每一次都归入两种成因之一，可由组装所增删的确切文本辨认。

**计划模式，±2345 字符，每周期两次——昂贵的那种。** 在 `7635e035` 中，组装于第 39 步增加六段（`4283 → 6628`），起始于「You are in plan mode. Stay in plan mode until exit\_plan\_mode succeeds」，并于第 49 步失去同样六段。`940cd8c9` 在第 23 与 36 步呈现完全相同的一对（`1763 → 4108 → 1763`），`691f01ce` 在第 46 与 50 步，另见 `15a62c0d` 与 `763dfbcf`。该文本块被插在 `git:` 工具段落之前而非任一端，因此被顶掉的余部包含它后面的每一个工具段落。由于计划周期在构造上发生于探索之后，两次付费都落在长对话上：`7635e035` 那两次分别重定价 115,683 与 146,074 个 token，而其首次请求代价仅为 7,112。

**禅模式晋升，−438 字符外加 25 个工具，每会话一次——由构造决定其廉价。** 在 `7635e035` 第 3 步，组装失去「Zen phase — the toolset is reduced while you anchor the task」，同时获得 `create_goal`、`exit_plan_mode`、`get_goal`、`interrupt_agent`、`list_agents`、`memory_deep_recall`、`memory_save`、`memory_search`、`ralph`、`repo_graph`、`semantic_search`、`send_message`、`session_event_read`、`session_event_search`、`session_event_trace`、`session_search`、`session_trace`、`skill`、`subagent_fork`、`task_kill`、`task_list`、`task_output`、`update_goal`、`web_search` 与 `workflow`。工具 schema 属于缓存前缀的一部分，所以晋升是一次完整失效——但它只花 14,185 个 token，因为它在第 3 步触发，此时对话还很小。同样的 `4721 → 4283` 与 `4958 → 4390` 签名出现在 `95b9dca1`、`54c42dc7`、`3330ae51`、`4bbcb226`，各一次且都在早期。这是计划模式应当效仿的形态，而不是用来对照它的基准。

第三种模式是 `reason="change"` 事件，其 header 与前一个逐字节相同。它不产生代价，属于日志痕迹而非失效。

## 提案

把随模式变化的文本移出系统提示词、放到请求的尾部，让缓存前缀终止于它之前，而不是横在它前面。

具体形态是一次 `agent/pre-step` 注入，在计划模式激活期间把策略正文作为模型最后读到的内容送入，同时让 `plan:policy` 要么不存在，要么退化为一个在会话内永不变化的常量。注入点之前的一切——身份、人设、工具指引以及整段消息历史——就在切换前后逐字节相同。

在系统提示词内部调整顺序不管用，也不应作为更省事的替代去尝试。把 `plan:policy` 抬到工具指引带之上确实能保住它前面的段落，但消息历史排在整个系统提示词之后，所以这个字符串里任何位置的改动仍会重定价每一条消息。只有把开关移到历史之后才有用。

注入采用合成消息还是供应商级后缀，取决于 `agent/pre-step` 的现有消费方在 spark 锚点注入上已经怎么做——那件事解决的正是相邻问题：把逐步内容放到不扰动前缀的位置。

## 考虑过的替代方案

**不管它：计划周期本来就少，而且是用户自己选的。**这是现状，也并非显然错误，因为一次计划切换是每会话几次的刻意行为。它落败于上面那份归因：`7635e035` 里两次切换就占了该会话未命中量的 53%，而用到计划模式的会话恰恰是那些缓存历史最值钱的长会话。稀少让它可以忍受，不等于让它便宜——每一次切换都是它所在会话中最贵的单个事件。

**像禅模式晋升那样，让切换尽早发生。**禅晋升同样是一次完整的前缀失效，它只花 14,185 而不是 146,074 个 token，纯粹因为它落在第 3 步。把计划模式约束在早期窗口，就能在不移动任何文本的前提下借来这个性质。它落败是因为这个约束在关键方向上无法成立：计划周期是对探索结果的回应，强制它提前，要么禁掉了合理的会话中途计划，要么逼用户重开一局。禅的形态成立，是因为锚定本就属于开头；计划不是。

**把段落改成常量——无条件发货计划模式正文。**这彻底去掉了开关，是可能的最小改动。它落败是因为这段正文是祈使且专属于该模式的：「Stay in plan mode until `exit_plan_mode` succeeds」「Do not edit or write files」。在计划模式之外发货它，会与组装里其他每一条指令相抵触——那正是无工具支撑的 `tool:<name>` 段落所造成的同一种悬空指引失败。

**接受重定价，但把段落改短。**把六段砍小能减少插入的字节，却减少不了作废范围，因为该偏移处的任何改动都会丢弃其后的一切。节省与段落长度成正比，而代价与历史长度成正比。

## 验收标准

一个进入并离开计划模式的会话，不因该切换记录任何 `request/header` 变化，且两次切换之后紧邻的步骤报告的 `cacheReadTokens` 与相邻步骤相当，而不是一个完全未命中的提示词。

对改动之后记录的会话重放同一份归因，「紧随 header 变化之后的一步」这一行在计划切换上应为零，可回收列中只剩禅晋升——而它的代价由第 3 步触发这一点封顶。

计划模式指令在计划模式之外的组装里保持缺席，因此模型永远不会被告知留在一个它并不处于的模式里。

## 风险

把指令从系统提示词移到消息尾部，会改变模型对它们的加权强度，而计划模式的保证恰恰属于「以对话身份到达时会被区别对待」的那一类。`exit_plan_mode` 必须是该轮最后且唯一一次工具调用这条规则，以及「对话式同意不构成批准」这条规则，是最可能被削弱的两条，且一旦削弱都有用户可见的后果。

该归因按「该步之前是否发生 header 变化」来切分未命中 token，这对前缀失效是正确的判别器，但它假定供应商自报的 `cacheReadTokens` 账目是可信的。它也无法把一次切换的代价与它所落在那一步的正常增长分开，因此单次切换的数字是上界，高出若干千 token。

可回收份额为未命中 token 的 13.1%，而后者本身是全部输入的 0.6%。用任何单个小时的账单绝对值来衡量它都会低估，因为失效恰恰集中在主导总支出的那些长会话里；用总体命中率百分比来衡量则会彻底掩盖它，因为 99.4% 与一次 146,074 token 的重定价是同一份度量。
