# @huiliyi37/dsh-memory-sqlite

English | [中文](README.zh.md)

Structured long-term-memory provider for the `memory` service (`@huiliyi37/dsh-memory`), registered under the same `memory` key as the Markdown provider — a composition mounts one or the other. Shipped TUI stays on Markdown; this package is on the tree for hosts that opt in. Storage follows the [structured LTM contract](../../../.agents/notes/implemented/feature/2026-08-18-memory-sqlite-structured-ltm.md): an **append-only event log** (`events`: kind fact/experience/observation/tombstone, keywords, entities, topic, confidence, sourceRefs) plus a **materialized fact view** (`facts`: subject/predicate/value, validFrom/validTo, confidence, status active/superseded/uncertain, supersedes, sourceEventId). Saving a different value under the same (scope, subject, predicate) supersedes the old version — invalidate, never delete; a partial unique index enforces one active fact per pair. `delete` tombstones (superseded + a tombstone event); nothing erases the log.

Retrieval is hybrid: FTS5 BM25 over text + keywords (CJK runs are bigrammed at index and query time so substring queries hit), exact `entities`/`topic` filters, scope and `excludeIds` filters, and temporal validity as a hard ordering — results sort by status tier (active > uncertain > superseded), then by normalized score: `relevance = -bm25 / (1 + -bm25)` (empty query: 1), `score = relevance × statusWeight` (active 1.0 / uncertain 0.6 / superseded 0.3). Every write or tombstone bumps only its topic's monotonic version; `topicVersions()` exposes the table for consumers that gate on topic change. The Markdown files under `<root>/.dsh/memory/` remain the human-edited source and are imported idempotently (per-file content hashes in the `imports` table) before every operation: edits and removals propagate as new versions and tombstones, and entries tombstoned via the API are not resurrected while the file is unchanged. The on-disk schema carries a monotonic `SCHEMA_VERSION`; old formats are rejected loud, not migrated.

An optional embedding layer (schema v3) upgrades retrieval to rank fusion. Configuring an embedder — the `embeddingProvider: 'http'` + `embeddingUrl`/`embeddingModel`/`embeddingApiKey`/`embeddingTimeoutMs` Config family (OpenAI-compatible embeddings endpoint), or any `EmbeddingProvider` from `@huiliyi37/dsh-semantic-index` injected as the plugin's third `apply` parameter, which wins over Config — makes `save` embed each new version's text once (one Float32 BLOB per fact version in the `embeddings` table, stamped with the embedder id) and makes `search` fuse the BM25 ranking with a brute-force cosine ranking over all filter-passing candidates via Reciprocal Rank Fusion (k=60), so paraphrases with no lexical overlap become reachable. The fused score is normalized — `fused = rrfScore / (2/(k+1))`: top of both lists = 1, top of one list = 0.5 — and `score = fused × statusWeight` flows through the same `score` field, so consumers that read `score` consume it unchanged; the status-tier ordering still ranks ahead of the fused score. The query is embedded at most once per `search` (never for empty queries or empty candidate sets); candidates whose stored vector is missing (Markdown imports and pre-embedder saves never embedded) or carries a stale stamp (the embedder model changed) are lazily re-embedded in one batch at search time — the documented rebuild path, no separate reindex command. With no embedder configured (the default) behavior is byte-identical to pure BM25 with zero extra calls, and embedding calls stay off the request path by construction: write-time inside `save`, query-time inside `search`.

A provider-free semantic-recall path needs no embedding endpoint at all: `keywordExpansion: 'llm'` spends one small chat-model call per `save` (route pair `keywordExpansionProvider`/`keywordExpansionModel`, required when enabled since the save path has no session route to derive from; `keywordExpansionEffort` defaults to `off` so reasoning models do not burn the output budget on thinking) generating 5–12 synonyms, paraphrases, and cross-language terms that merge into the entry's indexed keywords — original tags first (the `tags[0]`-as-topic proxy is untouched), expansions after, exact-deduplicated. Paraphrase queries (e.g. "重复收费" against an entry saying "扣款") then hit through plain FTS. Expansion is an enhancement, never a correctness dependency: an expander failure logs a log-only warning and the save proceeds unexpanded. An expander function injected as the fourth `apply` parameter wins over Config (the keyless test hook).

Conflict and retirement capabilities are for a later consolidation consumer. `markUncertain(scope, subject, predicate)` demotes the pair's current active fact to `uncertain` — no deletion, no supersession, retrieval keeps it at the lower weight — and appends an observation event so the audit trail records the conflict; a later save over an uncertain head supersedes it (fresh evidence resolves the uncertainty, one current version per pair). `retireStale(options)` counts one consolidation per call and retires superseded versions older than the caller-supplied retention horizon plus active/uncertain facts not surfaced by retrieval for the supplied number of consecutive consolidations (the use signal is `used_at_consolidation`, refreshed to the `meta`-table consolidation counter whenever `search` surfaces a version). `retired` facts leave `search` and `list` entirely; the rows and the append-only log stay, and retirement appends tombstone events and bumps the owning topic versions. Both are optional seam capabilities — consumers probe with `typeof memory.markUncertain === 'function'` / `typeof memory.retireStale === 'function'`.

## Model Experience

### Indirect — service surface only

#### What the model sees

Nothing directly: this provider never injects anything by itself. Memory content reaches the model only through consumers (`memory_save` / `memory_search` tool results, later STM snapshots).

#### Token effect

None directly; consumers render recalled entries at their own budgets. With an embedder configured, the provider spends one embedding call per `save` (an idempotent re-save spends the call and discards the vector) and one query-embedding call per `search`, plus at most one lazy re-embed batch when stored vectors are missing or stale-stamped.

#### KV Cache effect

No prompt structure contributed. Topic-partitioned versions let a consumer refresh only when a recalled topic actually changed, protecting the provider prefix cache.

## Known Limitations and Deferred Work

- **Brute-force vector scan** — with an embedder configured the cosine ranking scans every filter-passing fact; fine at memory scale (hundreds of entries), an ANN index is deferred. Fusion also changes score semantics: a hit topping a single list scores ≈0.5 where pure BM25 could reach 1.0, so consumers that gate on `score` need retuning when embeddings are enabled. The lexical channel is unchanged: CJK recall relies on bigram tokenization, so single-CJK-character queries do not match.
- **Single-process writes** — concurrent writers from two dsh instances on one cwd are not guarded; the store assumes one event loop.
- **Retirement needs a driver** — `retireStale` only runs when a consumer calls it; the store never retires on its own, and the search-time use signal makes retrieval a write on the view (not on the log).
