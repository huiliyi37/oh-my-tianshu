# opencode-tui (Tianshu TUI): a study of its end-to-end Chinese thinking and stable-flow mechanisms

English | [中文](opencode-tui-chinese-thinking-flow.zh.md)

This research document takes the external upstream repository `opencode-tui` (npm package `tianshu-tui`, CLI command `rivet`, local path `/Users/banxia/app/deepseek-tui/opencode-tui`, surveyed at snapshot v3.5.1, commit `199eef069`) as its subject, and dissects the evidence, design, and engineering trade-offs of its two mechanisms — "end-to-end Chinese thinking in the model" and "stable flow" — then, against this repository, tianshu-public (hereafter "this repo"), gives a gap list and tiered priority recommendations. Throughout, "upstream" paths are relative to the upstream repository root (e.g. `src/prompt/static.ts:4-8` denotes a line range); "this repo" paths are relative to this repository root. This research changes no code, copies no upstream content into this repo, and adds only this document.

## Scope and method

The research focuses on two points: end-to-end Chinese thinking (the model uses Chinese for reasoning and answers stably throughout the whole session) and stable flow (over a long session the model keeps making progress, without drifting, losing control, or hitting the context wall). The method is a read-only inspection of the upstream's real files: the system prompt and prompt assembly (`src/prompt/`), the wire-layer API client (`src/api/openai-client.ts`), the config schema (`src/config/schema.ts`), the runtime hooks (`src/agent/hooks/`, `src/agent/create-runtime-hooks.ts`), compaction and caching (`src/compact/`, `src/cache/`, `src/context/`), and the README and design docs (`README.md`, `CLAUDE.md`, `docs/architecture-overview.md`, `docs/compaction-tuning.md`). Core functionality is only sketched as context; the upstream's peripheral capabilities such as subagents, the star domain, and the desktop client are not expanded on.

## Upstream core functionality overview

The upstream is a full-featured programming-agent runtime deeply optimized for the DeepSeek V4 prefix cache: `package.json:4` describes it as `Terminal coding agent optimized for DeepSeek V4 prefix cache`, requires Node.js ≥ 24 (`package.json:23-25`), TypeScript strict, a pure ANSI TUI (`src/tui/engine/`) plus a Tauri desktop client and VS Code/Cursor plugins — three surfaces driven by the same core through the `src/server/` sidecar (`CLAUDE.md:13-16`).

`docs/architecture-overview.md:49-71` gives a six-layer architecture: Layer 0 multi-surface front end (TUI/desktop/plugins/headless/sidecar HTTP-SSE) → Layer 1 agent loop (`src/agent/loop.ts` → turn orchestration → tool execution → delivery, including the five-stage RuntimeHookPipeline) → Layer 2 context and cognition (`src/context/`, `src/memory/`: CognitiveLedger, ClaimStore, Stigmergy, PressureMonitor, etc.) → Layer 3 prompt and compaction (`src/prompt/`, `src/compact/`, `src/cache/`) → Layer 4 tools and repository intelligence (`src/tools/`, `src/repo/`, `src/search/`, `src/lsp/`) → Layer 5 model access (multi-provider adaptive routing, worker routing, the vision bridge) → Layer 6 data (SQLite session storage, `cache-log.jsonl`, `sensorium.jsonl` telemetry).

`README.md:312-316` summarizes three architectural pillars: the cognitive virtual machine CVM (model actions are filtered and corrected through 60+ conditionally assembled Hooks across the five stages preTurn / afterPerception / postTool / postTurn / postSession, with about 18+ active in a default session); the bio-inspired pheromone memory Stigmergy (behavioral footprints mapped onto code files as exponentially decaying signals); and prefix-cache optimization (frozen prefix + byte-stable appendix, 95–99% steady-state hit rate in long sessions). `README.md:318-328` gives engineering-quality metrics: roughly 208,000 lines of CLI source and 198,000 lines of tests (13,000+ node:test cases), tests : source ≈ 1 : 1. Core features (`README.md:330-550`) include: the prefix cache engine, API cost control, subagent orchestration (typed work orders, batch scheduling, team orchestration), tiered 50-tool presets, goal-driven auto-resume (`/goal`), Plan Mode (write lock + plan approval), the star domain system (16 switchable cognitive disciplines), Rewind, session handoff & resume (Handoff & Resume), the Council, the Skills system, cross-session knowledge, and MCP.

## End-to-end Chinese thinking mechanism

The upstream does not make "Chinese thinking" a switch; it splits it into four layers of anchoring, each countering a different cause of language drift: the identity layer sets the tone, the wire layer pins that tone into every API request, the token layer continuously supplies a Chinese identity stimulus at the tail of tool results, and the dosage layer backstops correction when a single turn injects a large amount of English. The shared premise of all four layers is **byte stability**: none of the anchoring means rewrite already-sent history messages; they only append to the tail of the request or the tool result, and therefore do not break the prefix cache.

### Layer 1 identity: Chinese identity and the thinking contract

The static base of the system prompt, `src/prompt/static.ts`, writes the entire `<identity>` block in Chinese and states the thinking-language contract explicitly at line 7: "When asked 'what are you' — you come from the Tianshu star domain and are currently advancing a task in some domain. You think and reply in Chinese." The base also includes sections such as `<beliefs>` (`static.ts:10-16`), `<stance>` (`static.ts:18-20`), and `<rules>` (`static.ts:22-96`), all written in Chinese — the language of the prompt itself is the first layer of anchoring. The subagent prompts carry the same Chinese contract, and the upstream test `src/prompt/__tests__/static-subagent.test.ts:247` directly asserts that the generated prompt matches "you think and reply in Chinese", showing that this is a test-pinned contract rather than incidental copy.

Comparison in this repo: `packages/core/system-prompt/README.md` explains that this repo's system prompt is assembled from ordered sections + tool schemas + variables, and that `deployment:persona` is the only config-level prompt fragment. It can be written in Chinese, but the SDK ships no language contract and performs no validation or testing of the persona's language.

### Layer 2 wire: the system suffix and the DeepSeek preserved-thinking protocol

The upstream appends a one-sentence Chinese thinking instruction to the tail of the system message in every API request, commented in `src/api/openai-client.ts:358-359` as `Stable suffix appended to system message for Chinese thinking (computed once, cache-safe)`:

```text
请在内部思考链中使用中文进行推理。不要在回复中输出你的推理过程，只输出最终答案或工具调用。
```

The generation condition is in `openai-client.ts:379-385`: the suffix is appended only when the config satisfies both `preservedThinkingProtocol` and `thinking === 'enabled'`; it is computed once at client construction and never changes afterward — byte stability is an explicit design goal, to avoid breaking the prefix cache.

The key to "end-to-end" thinking is the DeepSeek preserved-thinking protocol. The reasoning_content handling rules in `openai-client.ts:420-453`: preserved-protocol models (DeepSeek/MiMo) **echo back** `reasoning_content` on tool-call turns and strip it on plain-text turns; standalone reasoning models (GLM) always strip it; and it is always stripped when thinking is off. Echoing back ensures the model can continue the previous turn's chain of thought on every tool turn, instead of reasoning from zero each turn. Byte stability even extends to the field-absence case: `openai-client.ts:430-436` pads an empty string `reasoning_content: ''` for tool turns that should have reasoning_content but lack it — presence vs. absence changes the wire bytes and shatters the prefix cache at the next user boundary (the comment cites fix commit `8396ac51`). After stripping, DeepSeek requires the assistant message to have `content` or `tool_calls`; `openai-client.ts:446-452` fills in an empty `content`.

The config surface is in `src/config/schema.ts:13-25`: `thinkingBlock` (`enabled`/`adaptive`/`none`), `thinkingBudgetField` (`budget_tokens`), and `preservedThinkingProtocol` (comment in the source: `echo reasoning_content on tool turns`); `schema.ts:157-193` additionally has `thinking` defaulting to `enabled`, `thinkingStallTimeoutMs` (thinking-stall timeout), `slowThinking` as an explicit slow-thinking override, and the rule that temperature is not injected in thinking mode (most reasoning servers reject temperature adjustment).

Comparison in this repo: `packages/llm/llm-deepseek/src/serialize.ts:1-6` already implements reasoning_content replay (always echoed back on tool turns), and `packages/llm/llm-deepseek/src/translate.ts:21-31` already parses streaming reasoning deltas — the preserved protocol itself is already aligned. The gap is on the language side: this repo has no wire-level instruction for "use Chinese in the internal chain of thought", and no corresponding config key or byte-stability-constraint test.

### Layer 3 token: star signature

The upstream counters "training lock" (training-lock): when the model sees native tool names like `bash`, `grep`, and `git`, it tends to slip back into the English style that dominates its training corpus. `src/agent/star-signature.ts:1-15` records the design (idea E): do not rename the tools (that would break function calling), do not modify the prompt (prefix-cache safe), and work at the token level. The implementation appends a Chinese star-name signature to the tail of every tool result, in the format `── 星名（工具名）`, such as `── 执令（bash）`, `── 寻迹（grep）`, `── 史官（git）`, `── 观象（read_file）`, `── 织造（edit_file）`, `── 巡天（glob/repo_map/web_search）`, `── 试炼（run_tests）`, `── 分星（delegate_task）`, `── 铭刻（recall/todo）` (`star-signature.ts:17-58`). `src/agent/tool-pipeline.ts:808` takes the signature and concatenates it to the tail of every `tool_result.content` (e.g. `:953`, `:999`, `:2019`) — for every tool result the model processes each turn, the last token is a Chinese star-name association rather than raw shell output. The design deliberately chooses "token level rather than prompt level", continuously producing a Chinese identity rhythm without spending prompt weight.

Comparison in this repo: searching `packages/` finds no star-signature / star signature equivalent (negative search: `grep -r "star-signature\|starSignature\|星签名" packages/` has no matches). This repo has mechanisms that are similar in spirit but different in goal: the zen phase in `packages/guard/zen/README.md` constrains the opening with a minimal anchored tool surface; `packages/guard/task-card/README.md` rewrites the first user message into a structured task card.

### Layer 4 dosage: the language-anchoring hook and the advisory channel

Identity- and token-level anchoring can be diluted by a large amount of English content in a single turn. `src/agent/hooks/language-anchor-hook.ts:4-27` records the incident background (2026-07-02 postmortem `4e1aaa21`): a single 50KB English source-code dump flipped GLM's reasoning language to English and unlocked an RL "training-mode"-style enumerative CoT. The hook tallies the turn's cumulative tool output at the postTool stage: when non-CJK-dominant characters exceed a threshold (default 15,000, `language-anchor-hook.ts:36`) and the CJK character ratio falls below a floor (default 0.05, `:37`), it delivers a Chinese system-reminder through AdvisoryBus to re-anchor (`language-anchor-hook.ts:46-48`: "Language anchoring: this turn has injected a large amount of non-Chinese content … continue reasoning and answering in Chinese; lead with the conclusion and converge the key points"). The hook declares tier `priority=0.52`, higher than lossy-observation (0.48) and edit-tool-advisory (0.5), on the grounds that "identity drift is self-reinforcing (English reasoning reinforces itself)"; it delivers at most one per turn (`language-anchor-hook.ts:21-25`).

The carrier channel is AdvisoryBus (`src/agent/advisory-bus.ts`): it unifies five independent correction channels into a single `<星域-advisory>` aggregator (`:4-11`); three tiers — constitutional (never truncated) / operational / informational (at most 3 per turn, operational first) (`:14-16`); deduplication by key; priority 0–1 normalized ordering (`:66-70`); and a three-way delivery channel choice: `bus` (an appendix block, visible on the next request), `system-reminder` (appended into the message stream, must-read for the model, appended only to the tail without rewriting history — cache-safe), `status` (TUI status area only) (`:56-64`). Each advisory can carry an `expect` behavior predicate (`tool_appears`/`verify_attempted`/`file_touched`/`pattern_absent`/`course_changed`); at postTurn the advisory-readback-hook reconciles it against turn-level tool events and produces an adopted/ignored ledger, as the data foundation for countering habituation and reducing frequency (`advisory-bus.ts:21-54`).

Comparison in this repo: searching `packages/` finds no CJK-ratio detection or language-anchoring hook (negative search: `grep -r "cjkRatio\|CJK_RE\|languageAnchor" packages/` has no matches; the CJK matching in `packages/memory/memory-sqlite/src/fts.ts` is full-text-index tokenization, unrelated to language anchoring). This repo's guard family (`packages/guard/`: doom-loop-guard, repeat-tool-guard, evidence-gate, intent-bridge, task-card, timeout-policy, zen) is independent plugins each injecting its own reminders, with no unified priority bus, three-tier system, deduplication, or expect-reconciliation ledger.

### Supporting mechanisms: reasoning anchors and Chinese-output discipline

- Reasoning-anchor compensation: the wire layer truncates the front of reasoning_content, keeping only the tail N tokens (saving tokens and preserving cache); if the "excluded paths" inside the truncated part are not compensated, the model retreads old ground (a SAT conflict-clause analogy). `src/agent/reasoning-anchors.ts:1-12` extracts anchor sentences from the full reasoning and re-injects them via an `<excluded-paths>` block; after a resume path (resume/loadOai) they are rebuilt in full (`:41-54`).
- Chinese-output discipline is scattered across the side paths: the vision bridge `src/agent/vision-service.ts:15,22` uses "please analyze this image in Chinese / please process it precisely in Chinese"; the risk summary `src/agent/risk-explain.ts:61` requires "summarize in Chinese"; the review coordinator `src/agent/review-coordinator-deps.ts:366` requires "reply language: Chinese. Write all findings, summaries, and risks in Chinese"; the welcome assistant `src/server/greeting-route.ts:117` greets in Chinese.
- The context-injection protocol pairs with this: `src/prompt/static.ts:80-82` carries a `<rule name="context-update-protocol">` rule specifying that `<context-update>` blocks carrying a seq accumulate with override semantics, working with the incremental appendix to keep the model's sense of state stable.

## Stable-flow mechanism

### Prefix cache engine (the ice-mirror three zones)

The upstream fixes the first-principles constraint of "flow stability" on **byte stability**: DeepSeek bills a cache miss at up to 50× a hit, so the prompt engine is rebuilt around prefix-cache friendliness (`README.md:316`, `:332-343`). `src/prompt/engine.ts` splits the system prompt into three zones: `frozenBase` (the static base frozen within a session), `volatileBlock` (the dynamic zone), and the cross-turn incremental `appendixDelta` (`engine.ts:134-142`). The engineering constraints are in `docs/architecture-overview.md:75-86`: the appendix block must be byte-stable, with quantization done at the render layer; compaction history rewriting happens only at user boundaries (`turn===0`); a frozen snapshot commit must not depend on guards that `invalidateFreshCache()` can clear; and `stream()`'s transformation of the request must be copy-on-write (to prevent side-path re-entry from double-writing).

Supporting mechanisms (`README.md:336-340`): frozen prefix — the system prompt + tool definitions + stable context are frozen at session start and not rewritten within the session; incremental appendix — dynamic context is injected as cross-turn diff append blocks, roughly 200 bytes per-turn increment vs. roughly 5KB for a full rewrite; read-ref deduplication — repeated reads of unchanged files return a compact reference; cache-aware compaction — compaction keeps the first 2 messages as cache anchors; resume cache inheritance — the session frozen snapshot is persisted at every user boundary + shutdown, and read back on resume to feed the new engine, avoiding a full miss from byte 0. `README.md:343-354` gives diagnostics and fragmentation troubleshooting: `/debug cache`, per-turn hits in `cache-log.jsonl`, and full telemetry via `RIVET_DEBUG_TELEMETRY=1`.

Comparison in this repo: `packages/llm/cache-diagnostic/README.md:5-6` has already ported the upstream cache telemetry (derived from upstream `src/prompt/fingerprint.ts`, `src/prompt/cache-diagnostic.ts`, and the TurnCacheSnapshot in `src/agent/context.ts`) — **observation** is already aligned. The gap is in **discipline**: this repo's system prompt is re-assembled every step and allows `system-prompt/assemble` waterfall listeners to rewrite it (`packages/core/system-prompt/README.md`), with no frozen-prefix invariant, byte-stability contract, or resume snapshot-inheritance mechanism (negative search `grep -r "frozenSnapshot\|frozen-prefix" packages/` has no relevant matches).

### Context layering and the incremental appendix

The upstream models context as a layered system with stability grades. `src/prompt/context-layer.ts:34-48` defines 13 ContextLayerIds (system, tools, session-memory, historical-lessons, working-set, recent-raw-turns, current-request, project-instructions, git-status, tool-history, task-progress, behavior-mirror, decisions); `:49-51` defines three stability grades `stable`/`stable-volatile`/`dynamic`; `:74-88` defines a fixed layer order. Each layer carries a digest fingerprint and a token estimate (`:53-66`), supporting the judgment of "which layers changed and which layers can be frozen". `src/prompt/engine.ts:115-196` refines this further: the volatile layer is internally split into "latest-turn volatile" and "stable volatile"; the appendix carries a seq and a baseline; and the frozen snapshot maintains a fetch index keyed by user-message content (`frozenUserMerged`/`frozenFetchIndex`, `:158-162`).

Comparison in this repo: this repo already has the layering spirit (ordered sections, a replay-aware tokenMeter, workspace-context), but no explicit stability grades, layer fingerprints, or frozen-snapshot persistence.

### The five-rung compaction ladder and the cost-aware strategy

Compaction is where stable flow and cost intersect; the upstream's strategy is "don't compact if you don't have to, and when you do, make it pay". `CLAUDE.md:69` pins the five-rung ladder: session split → maybeCompact → T9 quality compaction → stale-round compaction → heap-driven micro-compaction, stopping at the first rung that triggers; compaction history rewriting happens only at `turn===0` (user boundary), and mid-turn only sets a pending flag deferred to turn 0; the 1M window skips/delays all rewriting; and `shouldDelayCompact` does not compact when the cache is healthy. `docs/compaction-tuning.md:52` records a 12-second debounced post-run background compaction that moves the latency of a synchronous full compaction off the next turn's critical path.

The cost-aware strategy is in `src/compact/compaction-profile.ts:4-21`: two orthogonal economic axes determine the reclaim floor — the billing axis (per-token-billed providers pay real money for cache-miss refills, so a rewrite must reclaim enough to be worth it; subscription providers pay only latency) and the cache axis (an exact-prefix persistent cache is destroyed by any history rewrite; partial/none caches lose little). It produces an absolute floor `minReclaimTokens` and a relative floor `minReclaimRatio` (`compaction-profile.ts:51-54`), and an action vocabulary `none/stale-round/micro/partial-llm/full-llm/session-split/checkpoint` (`:26-33`). Compaction is routed to a cheap model: `docs/compaction-tuning.md:9-25` and `src/config/schema.ts:552-564` define `compact.model` (default `deepseek-v4-flash`) + `compact.provider` — compaction is a one-shot, tool-free summarization task, so using the primary model both wastes tokens and evicts the main conversation's hot prefix cache because the compaction request's prefix differs from the main conversation; an independent provider/client = an independent server-side cache. `src/config/schema.ts:542-577` also defines the ratio-based policy (replacing the old `autoThreshold`) and T9 quality-compaction thresholds: 0.55 for per-token-billed providers, 0.45 for subscription, and a 0.6 subscription ceiling (`:569-575`); the emergency paths (session split, 95% ceiling) are not constrained by the `enabled` switch (`:542-545`).

Comparison in this repo: `packages/compact/compact-basic/src/summarizer.ts:30-32,114-116` already implements prefix-cache-reusing compaction (replaying the session prefix + the compaction instruction as the last user message, reusing the provider's hot prefix), and `compact-tool-result-prune` performs model-free result pruning. The gaps: this repo has no five-rung ladder, no turn-0 boundary coordinator, no cost-aware reclaim floor (billing × cache axes), no per-provider-tiered ratio policy, and no compaction-specific cheap-model routing (a negative search finds no equivalent config key).

### CVM runtime hooks and AdvisoryBus

The "intervention layer" of stable flow is the CVM: `docs/architecture-overview.md:70-73` explains that roughly 60+ hook modules are conditionally assembled under deps/environment-variable gating, with about 18+ actually active in a default session; the resident baseline includes perception, signal-consumer, kick, vigor, theta, stigmergy, radio; advisory-type hooks inject system-reminders through AdvisoryBus and **do not rewrite** frozenBase/volatileBlock. The real five-stage call sites are pinned in `CLAUDE.md:30-37`: preTurn / afterPerception → `turn-perception.ts`, postTool → `tool-execution.ts` (after each tool execution), runCompaction → `turn-orchestrator.ts` (after postTool, before postTurn). `src/agent/create-runtime-hooks.ts` is the assembly catalog (excerpts): preTurn's intent-anchor (long-autonomy-run intent anchoring, `:725`), turn-budget (maxTurns danger zone, `:747`), reasoning-spiral guard (single-turn reasoning spiral, `:820`), spec-verify gate (`:898`); postTool's lossy-observation (truncated-output discipline, `:597`), dead-end detector (repeated edit→verify-fail on the same file, `:676`), probe-discipline (`:688`), script-iteration (`:695`), batch-convergence (`:706`), regression-bisect circuit breaker (`:713`); postTurn's self-verify (`:547`), typecheck-reminder (`:904`), todo-reminder (`:911`), wrapup-anxiety guard (wrap-up anxiety talk × measured ctxRatio, `:862`), advisory-readback (`:760`); postSession's essence-gate (knowledge-admission gate, fail-closed no-write by default, `:457`), recall health ledger (`:463`), dream/skill-distill (`:442`).

Comparison in this repo: this repo's Cordis event system and the `packages/guard/` family are mechanistically equivalent to a "one plugin per guard" shape, already having specific guards such as doom-loop-guard, repeat-tool-guard, evidence-gate, and timeout-policy. The gaps: no unified priority bus (three tiers, 0–1 priority, per-key deduplication, per-turn count cap), no expect predicate or adopted/ignored reconciliation ledger, and no datafied "reminder → behavior → frequency reduction" closed loop; some guard scenarios (wrap-up anxiety, reasoning spiral, intent anchoring, compaction amnesia) have no counterpart in this repo.

### Session-level flow facilities

- Goal-driven auto-resume: `/goal` starts GoalTracker, integrated with the turn loop, doom-loop detection, and the delivery gate (`README.md:397-404`); goal completion is verified by an independent judge, and `src/config/schema.ts:522-532` defines `goal.judge.enabled` (default true, independently verifying a self-claimed completion), `maxRuns` (default 3, guarding against an accept/reject loop), and `browser` (Phase 2 browser verification, default false).
- Plan Mode: after entering, write operations are locked; research → a structured plan written to `.rivet/plans/<slug>.md` → `/plan-approve` approval → wave-by-wave execution → `/plan-close` settlement (`README.md:406-431`).
- Session handoff & resume: `/handoff` generates a fixed five-section handoff document (task goal / completed / current blocker / next step / pitfalls, each entry carrying `file:line` evidence and a verification command), archived as `<id>.handoff.md` after the turn completes; a handoff is prompted when context occupancy ≥50%; on `--resume` the handoff document is auto-injected, the frozen prefix is inherited, write evidence is repaired (preflight synthesizes the interrupted orphan tool result), and model affinity is applied (resume switches back to the original session model to reuse the per-model cache namespace) (`README.md:471-497`).
- Rewind: double-pressing ESC selects any past user message and cleanly rewinds the session to that point (`README.md:467-469`).
- Permission checkpoints: Auto mode can be set to pause every N turns and synchronize a progress summary (which files changed / token usage), continuing after confirmation (`README.md:265,295`); five approval levels (`src/config/schema.ts:362`), `maxTurns` default 200 (`:370`), `crossSessionEnabled` default true (`:416`).
- Cache-warmth prediction: the SessionWarmthTracker in `src/cache/session-warmth.ts:10-22` predicts cold/hot cache temperature from the time since the last API call (TTL default 1 hour), for use in compaction/resume decisions.

Comparison in this repo: the goal subsystem (`packages/goal/`: goal / goal-session / tool-goal / command-goal) and the plan package already exist, but goal-session is a same-session resume driver (`packages/goal/goal-session/README.md`), and searching `packages/goal/` finds no independent completion judge; session resume goes through event-sourced replay (`packages/core/session/`), with no handoff-document closed loop (negative search `grep -r "handoff" packages/` has no session-handoff semantic match); rewind already has an overlay in the TUI (`packages/tui/tui/tests/rewind-overlay.spec.ts`); permission checkpoints and session warmth have no counterpart.

### Cross-session knowledge

`README.md:528-536`: `.rivet/knowledge/memory.jsonl` stores project rules, debugging heuristics, and architecture conventions; `.rivet/sessions/<slug>/<id>/pheromones.json` stores intra-session pheromones; `agent.crossSessionEnabled` is the master switch. On the write side there is essence-gate (the postSession knowledge-admission gate; unassembled by default = fail-closed with no writes, `create-runtime-hooks.ts:135,457`) and a recall health ledger (postSession aggregates the empty-recall rate / citation rate to disk, `:463`). Pheromone (Stigmergy) is intra-session spatial memory where "behavioral footprints map directly onto code files and decay over time", distinct from the static MEMORY.md (`README.md:315`).

Comparison in this repo: this repo already has a pheromone equivalent `packages/guard/pheromone/README.md` (a file-level stigmergy store with exponentially decaying signals, 7-day half-life by default) and the memory family (`packages/memory/`: memory, adaptive-memory, memory-consolidate, memory-pipeline, memory-sqlite, tool-memory-recall). The gap: no essence-gate-style fail-closed knowledge-admission gate and no recall health ledger (the aggregate empty-recall-rate / citation-rate feedback loop).

## Harness engineering notes

### Six-layer architecture and the multi-surface shared core

The upstream's harness shape is "one core, many surfaces": the TUI, the Tauri desktop client, and the VS Code/Cursor plugins all drive the same agent core through the `src/server/` sidecar (`CLAUDE.md:13-16`), with the headless mode `rivet -p` for script integration (`README.md:130-158`). The agent loop main path is pinned in `CLAUDE.md:30-37`: `main.ts → AgentLoop（agent/loop.ts）→ RuntimeHookPipeline`, with the hook executor purely phased + error-isolated (a thrown hook error goes only to onError and does not interrupt the turn). The tool registry `createDefaultToolRegistry` maintains a kernel budget ≤ 26, beyond which cognitive-overload degradation triggers (`docs/architecture-overview.md:88-98`); presets assemble in tiers (minimal 29 / frontend 30 / full 50 / taiyi 16, `README.md:376-394`).

Comparison in this repo: this repo's harness is the plugin-based shape of vendored Cordis (`docs/architecture.md`: everything is a plugin, including the loop), where events are the extension API and session events can be durably replayed; the shapes differ but the engineering disciplines are close (error isolation, registration is an effect, model-visible ⟺ logged). This repo has no kernel-budget concept (the tool surface is managed by zen phases and restrict), and no multi-surface shared sidecar (`packages/api/` and `packages/client/` are a different integration shape).

### Model access and adaptive routing

The upstream is multi-provider (DeepSeek/DeepSeek Spark/Claude/GLM/Codex/MiniMax/MiMo, `README.md:164-177`), with in-session `/model` switching; worker routing assigns subagents different models by profile (capable/cheap) (`README.md:242-254`); and subagent orchestration adaptively selects models by profile pass rate + latency score (`README.md:370-374`). Cost control (`README.md:356-364`): default reasoningEffort downgrades (V4 Pro max→high, Flash max→medium, explicit config protected by `reasoningFloor`); effort routing is on by default (routine low-complexity + high-confidence turns auto-downgrade one notch, never up); and doom-loop auto-convergence injects stricter output-style constraints. The vision bridge (`README.md:207-240`): when the primary model cannot see images, `agent.visionModel` bridges, with a fallback bridge, automatic bridge selection off by default (a privacy decision), and images appended to the conversation tail without interrupting the prefix cache.

Comparison in this repo: `packages/llm/` has adapter registration and the `reasoningEffort` request-header state (`packages/llm/llm/src/call-config.ts`), `packages/core/model-roles/` pins vision/secondary/subagent roles, and `packages/guard/agent-router/` has MoE routing. The gaps: no effort routing of "auto-downgrade by task complexity, never upgrade, explicit max is the floor"; no adaptive worker routing by profile pass rate + latency (this repo's subagents go through named-delegation providers and workflow scripts); no thinkingStallTimeout (negative search `grep -r "thinkingStall" packages/` has no matches).

### Engineering quality and observability

### Tiered adoption recommendations

- Wave 1 (Chinese thinking, small investment, direct payoff): add a configurable Chinese-thinking contract to `dsh-system-prompt` (persona template + test-pinned), add a preserved-protocol-gated Chinese-thinking suffix to `dsh-llm-deepseek` (reusing the upstream "compute once, byte-stable" approach), and add the config key to `dsh-llm` (`preservedThinkingProtocol` already has the capability bit; only the language suffix needs adding).

- Wave 3 (flow discipline): first add frozen-prefix observation (cache-diagnostic already has fingerprints), then argue whether to introduce the frozen-prefix invariant and resume snapshot inheritance; in parallel, abstract AdvisoryBus's priority / deduplication / reconciliation ledger into a reusable guard infrastructure for this repo (if the existing guard plugins need it).
- Wave 4 (compaction and resume): on `dsh-compact`, argue the cost-aware reclaim floor and dedicated cheap-model routing (the upstream's billing × cache two-axis analysis is directly reusable); the handoff-document closed loop can be a small standalone feature on top of goal/plan.
- Explicitly not recommended to copy wholesale: the star domain system, the Council, and the full CVM hook suite (redundant with this repo's Cordis plugin shape); the upstream 50-tool presets organize the tool surface differently from this repo, so borrow individual items as needed.
